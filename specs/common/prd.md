## 1. 产品目标与用户

### REQ-01 固定工作流定位

面向需要初步了解企业公开线索的普通用户。用户通过公司名称检索、确认主体、查看线索、浏览官方页面并手工补充材料，取得来源可追溯、结论有边界的中文分析报告。

应用不提供自由对话入口。LLM 是受控文本分析节点，只读取本次批准进入分析的输入，不自行检索、调用企业接口或浏览官网。

报告回答：当前材料支持哪些事实或解释、哪些线索冲突、哪些事项尚不清楚。材料不足时明确不足，不追求每次都生成完整企业判断。

## 2. 本轮决策与首版范围

### REQ-02 已纳入的产品决策

| 决策 | 本稿采用的规则 |
| --- | --- |
| 官网复核 | 常驻“在新标签页打开官网”入口；应用内不嵌入官网、不抓取或解析网页 |
| 单候选 | 和多候选一样，用户确认主体后才发起详情查询与分析 |
| 主体不匹配 | 录入仅留作当前会话待修改草稿，不进入当前主体证据包、不分享、不刷新报告 |
| 共享准入 | 主体代码匹配、来源链接与查看时间完整、用户主动同意共享；内容仍是系统未核实的用户线索 |
| 部分查询失败 | 展示取得的有效材料并允许有限分析，逐项说明未覆盖类别，不能表述为无风险记录 |

### REQ-03 首版能力

- 公司名称搜索、候选卡片与人工主体确认。
- 天眼查授权接口查询及按类别显示取得情况。
- 三类来源证据卡片、他人快照预填充与知情确认。
- 手工录入、当前会话保存、可选共享、自动重新分析。
- 一次分析结束返回完整结果，由前端同时更新主体、证据、报告和提示。
- 失败重试、重复提交保护、主体/会话隔离及报告版本提示。

首版不包含自由聊天、自主 Agent、官网采集、截图 OCR、自动风险评分、企业排行榜、估值/投资推荐、支付、复杂账号中心和运营后台。不引入生产环境部署或外部账户开通任务。

已采用的默认值：共享快照仅在来源查看时间与共享提交时间均距当前未满 7 天时可供预填充；到期退出共享查询并删除共享记录。当前会话仅保留至明确结束或最后操作后 24 小时；重置会话即删除会话草稿与分析结果。具体存储与清理验证由 SDD 定义。期限不代表材料在此期间必然准确或最新。

## 3. 主流程

### REQ-04 搜索与主体确认

1. 用户输入公司名称并提交；空白输入不发出搜索请求。
2. 展示候选结果；候选数量为 1 或多条时均需用户点击确认。
3. 主体卡片展示全称、统一社会信用代码、注册省市、法定代表人、成立日期；缺项直接标明，不补造。
4. 主体无有效信用代码时不可进入详情查询，提示重新搜索或选择其他候选。
5. 零候选显示“本次未返回匹配企业”，不等同于该企业不存在；搜索错误单独显示并支持重试。
6. 后端核验确认的是本次搜索返回的候选，不能相信客户端任意拼接的主体字段。
7. 详情响应与当前已确认信用代码矛盾时，不纳入证据，提示主体校验失败；不得自动更换主体。

用户发起新搜索时保留当前主体已完成结果，直到确认切换主体。切换需确认会清除当前未提交草稿；切换后不携带旧主体草稿、证据、查询状态或报告。

### REQ-05 详情查询与覆盖状态

确认主体后，按应用已配置且获授权的数据类别串行获取资料。首版拟覆盖工商、经营异常、行政处罚、司法/执行、资产受限线索；是否具备对应接口，以官方文档、账号权限和实际返回样例核验为准。不得把未购买、未配置或未查询的能力展示成已查询无记录。

每类数据记录以下用户可观察状态；精确字段由 SDD 定义：

| 状态 | 含义与显示要求 |
| --- | --- |
| 有数据 | 查询成功并取得该类别有效记录 |
| 无返回记录 | 查询成功，该类别未返回记录；不代表不存在风险 |
| 查询失败 | 超时、鉴权、限额、响应异常等导致未能完成查询 |
| 未查询 | 本次没有查询该类别，写明未覆盖 |

整体 `tianyan_status` 保留 `ok / empty / error`，并新增 `partial` 表达混合覆盖：

- `ok`：本次计划内各类别均查询成功，至少取得一条有效详情记录。
- `empty`：本次计划内各类别均查询成功，全部未返回有效详情记录。搜索阶段主体卡片不计入详情记录。
- `error`：本次计划查询的类别全部失败。
- `partial`：计划内类别有成功也有失败，或未完成计划查询；不能伪装成 `ok` 或 `empty`。

计划范围必须展示。未配置类别显示“未查询”，不纳入本次计划，但仍属于报告覆盖缺口。计划内接口不接受因权限不足而悄悄缩小覆盖范围。

### REQ-06 快照预填充

仅整体 `tianyan_status=empty` 且存在当前信用代码的有效他人共享快照时，预填充手工录入表单。其他状态不自动加载共享快照进入表单或报告，用户仍可主动手工录入。

- 默认选取最近提交且未到期、未撤回的匹配快照；展示来源链接、原始查看时间、共享提交时间和“他人提供，系统未核实”标识。
- 预填充只是待确认草稿，不进入证据包，不自动触发 LLM。
- 知情确认默认不勾选。确认意味着用户理解材料来自他人、可能过时、系统没有核验原网页；不代表系统证明其真实性。
- 用户可以确认并使用、修改后提交或清空改为自行录入。未确认或表单非法时提交按钮不可用，服务端也必须拒绝绕过确认的提交。
- 快照查询失败时展示提示，不阻止用户自行录入；不能声称不存在共享材料。

### REQ-07 首次报告

取得有效证据后自动触发分析，无需用户输入问题。共享预填充未确认时不参与分析。

若证据包为空，展示主体和查询覆盖状态，提示补充材料，不调用 LLM 生成实质性报告。仅确认公司名称/代码不算已具备可分析的业务线索。

每次分析完成统一返回完整结果：`subject`、`evidence_list`、`summary_text`、`api_status`、`ui_hint_group`。查询/生成期间可以显示进度状态，但不将未完成文本片段当作正式报告。

## 4. 手工线索与共享

### REQ-08 录入与归属

表单采集：线索正文、来源记录所指企业的信用代码、来源链接、来源查看时间，以及自愿共享选择。查看时间采用用户本地时区输入并明确展示时区，不允许未来时间。事件发生时间若知道可以补充，不能用录入时间替代事件时间。

- 正文和主体代码必须填写；正文中的其他明确企业代码若与所填代码发生归属冲突，保留为待核验草稿，不能自动分配归属。
- 来源代码缺失或与当前主体不匹配，保留草稿并解释原因，不加入报告；不把空缺猜成当前代码。
- 代码匹配只建立用户声明的主体归属，不是内容真实性认证。
- 匹配的自行录入可仅用于当前会话。来源链接/查看时间缺失时明确显示缺项，不能共享。
- 只有匹配、字段完整、显式同意共享的提交才可写入共享缓存。共享选择默认关闭，与“接受他人快照”的知情确认分开。
- 来源 URL 仅作为用户提供的定位信息校验格式，不由系统访问页面或核验内容；不能因为 URL 属于官方域名就将录入升级为官方原文。

### REQ-09 来源与衍生关系

每条证据保留稳定编号、主体归属、内容、取得渠道、时间、来源链接及已知局限。原始发布者与录入渠道分别表达，详细结构在共享 Schema 中定义。

| `source` | 含义 |
| --- | --- |
| `tianyan` | 天眼查接口返回的聚合资料，非本应用核验的官方原始公示 |
| `user_other` | 其他用户录入、当前用户确认使用的快照；仍未核实 |
| `user_self` | 当前用户自行录入的内容；提供链接也不自动成为官方记录 |

确认使用未修改的他人快照仍为 `user_other`。修改其内容后提交的新记录可为 `user_self`，但必须保留衍生自原快照的关联和未核验说明；原快照与衍生记录不得被计算为独立互证来源。

`hint_id` 用于引用提示文案，不作为证据编号或业务事实。缺少来源或日期时显式说明，不让模型补填。

### REQ-10 保存、共享与自动刷新

主体匹配的线索保存到当前会话后，更新证据版本并自动重新调用 LLM。无需额外提问或点击生成。每次重新分析只读取本次会话已接纳的证据，不自动吸收其他用户后续共享内容。

- 同一次提交重试不得重复增加证据、共享记录或生成任务。
- 保存成功但 LLM 失败时，证据仍保留，分别提示保存成功与报告生成失败，支持对当前版本重新分析。
- 会话保存成功但共享写入失败时，线索仍可分析，明确提示未共享成功，不能假报共享完成。
- 不同用户的内容不相互覆盖。不对冲突内容自动判真伪或按票数采信。
- 共享提交者可通过本次共享回执撤回自己的记录；他人不可撤回。撤回记录不再被后续预填充；已经被其他会话接纳的副本不追溯抹除，但不得再用于新增共享。
- 用户身份归属、会话访问与回执权限由服务端验证，不能靠客户端自报 `source`、用户 ID 或共享状态取得权限。

## 5. LLM 分析行为

### REQ-11 输入、方法与输出

输入为当前主体、已接纳证据包和查询状态。节点每次携带固定系统规则；证据正文和链接属于待分析数据，其中的“忽略规则”“请上网查询”等文字不能成为系统指令。不向节点配置检索、浏览或企业接口工具。

分析采用理性克制、溯源优先、通俗解释的方法，不对外冒充真实创作者本人：

1. 先提醒主体误认和公开信息局限。
2. 基础事实和逐条线索标记来源，重要事实引用输入中存在的证据编号；主体字段可引用输入主体信息，不编造对应证据编号。
3. 重要主张按“证据支持—反向/冲突线索—替代解释—目前判断—关键缺口”组织。没有材料的维度明确不知道，不强行填全。
4. 区分认缴、实缴与当前现金；区分同一事件不同阶段、不同主体及不同期间。
5. 官方原始材料未被系统核验时，不声称已经核验或已经全面检索官网。
6. 区分事实、推断和未知。不评分、评级，不贴“靠谱/骗子/高危”等企业标签，不猜动机。
7. 以“仅供公开线索初步筛查，不构成投资、合作决策建议”收尾。

非上市并不等于没有法定公示义务；同名主体提醒不使用“不同省市必然可以登记完全相同全称”的绝对表述。来源按形成者、事项、时间和核验情况判断，不把全国平台机械排在地方原始决定之前。

应用可以校验报告是否包含必要段落、引用是否存在、是否出现明显越界内容；不改写已经接收的模型原文。不合格报告不作为成功报告发布。校验的能力边界必须在 SDD 与测试中说明，不能保证自由文本绝无事实错误。

### REQ-12 失败与一致性

- 没有可分析证据：`summary_text` 为空字符串，报告区解释材料不足；状态区别于 LLM 调用失败。
- 首次生成失败或输出未通过校验：`summary_text` 为空字符串，显示失败原因类别和重试入口，不伪造报告。
- 新证据已保存但重分析失败：可展示上一版成功报告，但必须注明其旧证据版本和“未包含最新录入”；当前版本报告状态为未完成，不能假装已刷新。
- 主体、证据、查询覆盖和报告均绑定当前会话、已确认主体与版本；旧主体或旧版本的迟到响应不得覆盖当前结果。
- 用户重复点击或网络重试不得产生相同业务操作的重复副作用。用户可停止等待；返回页面后显示实际完成状态，不把“停止等待”等同于已取消服务端调用或费用。

## 6. 文案、官网入口与安全边界

### REQ-13 官网入口

搜索、候选、结果和录入阶段均可见“打开官方公示网站”入口，点击后在新标签页打开选定官网。官方链接以受控列表维护，不自动代填/提交企业查询，不读取官网页面、DOM、剪贴板、截图或网络响应；用户主动在本应用表单粘贴/输入的文字除外。

新标签页打开失败时允许复制官网地址并提示手动访问。切回应用保留当前会话、主体和表单草稿。正式官方地址在 SDD 阶段核验后写入配置/字典，不假定网站提供直达某企业的稳定 URL。

### REQ-14 提示与信息展示

全局提示、警告和固定文案由 `text-dict.json` 统一维护。`ui_hint_group` 表达本次应显示的提示项，证据通过 `hint_id` 关联必要说明；提示代码由应用确定，不让 LLM 临时创造或解释业务状态。

来源颜色只区分取得渠道，不表达企业风险等级或信息已被认证。报告的业务事实来源必须来自输入，而非提示字典。

密钥由服务端保存。不同会话的私人草稿、查询和报告不可互相读取；仅明确同意共享且符合准入条件的线索可进入共享范围。日志不得泄露密钥或未授权扩散用户正文。

| AC-05 | REQ-05、06 | 只有整体 empty 可触发他人快照预填充；error、partial 不自动预填充 |
| AC-06 | REQ-06 | 未勾选知情确认不能提交预填充；直接绕过前端提交同样被拒绝 |
| AC-07 | REQ-06、07 | 待确认快照不进入 LLM；没有有效证据时不生成实质性报告 |
| AC-08 | REQ-08 | 缺代码、不匹配或归属冲突仅留草稿，不分析、不共享 |
| AC-09 | REQ-08、10 | 未主动同意或缺来源链接/查看时间的录入不共享；合法会话录入仍可分析 |
| AC-10 | REQ-09 | 三类来源正确标记；用户确认不升级为官方资料；衍生快照不当独立互证 |
| AC-11 | REQ-10 | 同次提交重试不重复增加记录；保存、共享、LLM 刷新分别如实反馈 |
| AC-12 | REQ-11 | 不评分、不编造事实/链接/引用、不执行证据中的指令；有开篇提醒和结尾说明 |
| AC-13 | REQ-11 | 同一案号的多阶段记录不重复解释为多个独立事件；无证据维度明确未知 |
| AC-14 | REQ-12 | 生成失败可重试；旧报告标明旧版本；迟到结果不能覆盖当前主体与新版本 |
| AC-15 | REQ-13 | 官网在新标签页打开；应用没有官网采集/解析路径；返回后草稿仍在 |
| AC-16 | REQ-14 | 提示由字典定位，来源样式不被渲染成风险等级；跨会话私人数据不可读 |
| AC-17 | REQ-03、10 | 共享记录到期/撤回退出后续预填充；会话重置清除当前私有草稿和结果 |

这些是需求验收条目，不是已运行或已锁定的契约测试。后续 SDD 需逐条建立模型/接口、骨架与测试映射。

## 8. 后续产出与外部依赖

PRD/UI 评审通过后：编写前后端 SDD、共享 Schema 与数据状态契约，再依次进入骨架和契约测试评审，最后实现。

用户要求的六项交付按用途归档：分析方法论与提示词位于 `specs/analysis/`（`skill.md`、`llm-system-prompt.txt`），输入输出与文案位于 `contracts/`（`input-schema.json`、`output-schema.json`、`text-dict.json`），验收场景位于 `tests/test-cases.md`。方法论文件只写分析思维；工程状态、缓存、接口和 UI 行为归项目规格。机器 Schema 只有一份权威定义。

待在 SDD 锁定前完成的核验：天眼查具体接口、授权与分页/覆盖；LLM 接入与错误返回；官网地址；会话和共享回执权限；超时/重试上限、数据清理及报告校验可验证边界。可以先基于明确的依赖能力编写待评审规格，但在这些契约未明确前不能伪装完成真实集成。
