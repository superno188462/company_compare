## 2. 目标、范围与 UI 基线增补

### WINDOW-SCOPE-01

解决司法案件数量大于 200 时整类零接纳的问题。首批司法查询仍固定覆盖失信、被执行、限制消费、司法案件、裁判文书、法院公告 6 个子工具，但每个子工具本次最多取得第一页 20 条，类别最多 120 条；只分析本次实际接纳的记录，并明确未查全。

本批不自动翻完数千条，不新增“继续加载”或付费批量工具，不购买 SVIP，不扩大其他四类的查询范围，不接入其他商业供应商，不新增官网抓取。后续全量浏览/按条件筛选属于独立需求，不把本批有限查询描述成已解决全量浏览。

### WINDOW-UI-01

沿用现有“资料取得情况”，司法类别新增“部分取得”状态。就地可展开子工具覆盖表：中文工具名、已纳入条数、上游声明总数（未知则“未提供”）、是否尚有记录或查询失败。示例：“司法案件：本次纳入 20 条；上游声明共 5564 条；其余未查询”。其他子工具单列，不能将案件总数标成司法全部记录总数。

部分取得时展示固定提示“以下分析只覆盖已取得材料，未查询部分不代表没有风险”；提供既有官方复核入口。原“重新查询”允许用于 error/partial，含义是重新取得同一范围并替换本类别当前批次，不是追加下一页。任务中禁用重复操作，展开覆盖不发请求。其他页面、草稿与布局不变。

## 3. 外部依赖

### WINDOW-DEP-01

继续使用既有 CompanyDataPort、天眼查 Shared Core、会话存储、时钟与模型端口。司法依赖需返回实际 items、页码/页大小和声明总数；总数不是账户额度，也不保证独立案件数。`_truncated` 或不完整分页不能忽略；只有可证明完整的单页才记 complete。

本批不依赖实时能力目录把业务标为空。能力目录提供的“未查询到记录”仍只是目录信息，不用于把明细失败改写为 empty。

## 4. 数据模型与 Schema 变更提案

### WINDOW-DATA-01

既有 CategoryResult.status 新增 `partial`；原值 ok/empty/error/not_requested 不变。`record_count` 仍表示本轮实际接纳数，0..200。partial 允许 0 条（例如部分子工具查询成功为空、其他子工具失败）；error 仍为本轮 0 条且未取得任何可靠子范围。只有所有计划子工具与所需分页都完整才为 ok/empty。

CategoryResult 新增可选 `tool_coverage`，默认 []，最多 6 项（首批仅司法类别使用）。每项 ToolCoverage：

| 字段 | 类型 / 语义 |
| --- | --- |
| tool_name | 必填；既有司法 6 个工具名枚举，不接受任意字符串 |
| status | complete / empty / partial / error / not_requested；分别为完整且有记录、完整空、已取得有限范围、该子工具失败、因本轮预算未请求 |
| accepted_count | int 0..200；实际纳入当前证据包的数量，所有子工具之和等于类别 record_count |
| total_count | int >=0 或 null；上游声明的本工具总数，未提供或不可信则 null；不同工具总数不相加宣称独立案件数 |
| has_more | bool 或 null；已知仍有剩余为 true，能证明完整才为 false，不确定为 null |

分类 partial 时 error_code：仅因为主动限制查询范围则 null；包含失败子工具则记录本类别第一个明确错误。query_diagnostics 可对包含失败的 partial 类别保留当前第一个失败的安全诊断，不进入 LLM。部分范围本身不是 HTTP 查询失败，不凭空生成失败诊断。

ProviderCategoryBatch 新增可选 completeness=complete/partial（缺省 complete）、tool_coverage=[]。CompanyDataPort.fetch_category 增加可选关键字参数 record_limit（缺省 200），调用司法时传实际剩余容量，司法窗口最多取 min(record_limit,120) 条；其他类别调用方式及规则不变。现存替身的签名适配在类型/测试阶段列出，不擅改锁定用例。

类型映射：为承载上述“partial包含失败子工具时保留第一个错误与安全诊断”的已批准行为，批次还声明 error_code: ProviderFailureCode | None = None、diagnostic: QueryDiagnostic | None = None。它们仅在服务端适配器到应用服务间传递；模型输入仍只有覆盖字段，diagnostic 不进入模型。该映射随类型评审包一并核对。

输入 Schema 同步新增 partial 与覆盖字段，使模型知道材料不足。输出 Schema 引用同一权威定义；不能只改前端输出而让模型误以为已经完整。旧 payload 不含新字段仍合法，默认没有子范围详情；本次不推断历史覆盖。

## 5. 接口与业务分支

### WINDOW-IF-01 初查与容量

1. 主体确认、信用代码归属与固定 6 工具计划保持。司法窗口总预算取 min(120, 200 - 当前需保留证据条数)，不得挤掉已接纳的用户或其他类别证据。
2. 剩余容量为 0 时不调用司法明细，返回明确应用容量不足错误，不标 empty。旧司法证据替换时只释放本类别平台记录所占容量；用户线索不释放。
3. 固定工具顺序不变。每个列表工具只请求第一页，页大小 min(20,当前剩余容量)；空响应不占用预算。一个工具失败继续其余已计划工具，禁止单个失败清空其余工具已取得的有效证据。
4. 响应页内所有记录必须先通过归属、结构、长度和唯一性校验才能接纳该页。上游多返记录、来源分页异常、页内重复、错配或超长时该子工具失败，不能静默裁剪。其他已通过子工具保留。
5. `total_count` 大于已取得数量、返回截断信号或不能证明完整时，本工具为 partial。所有 6 项均 complete/empty 才能把类别记为 ok/empty；有任何未完成且存在可靠子范围则为 partial；全失败则 error。
6. 没有明确时序契约时不宣称“最新 20 条”。按上游第一页顺序保留，不宣称随机样本或代表总体。

### WINDOW-IF-02 重查、报告与整体状态

继续沿用现有 retry-queries HTTP 方法与任务句柄；将可重查类别从仅 error 扩展到 error/partial，仍不允许对完整成功类别误用失败重查。

同键同请求回放同一任务；重查有可靠部分/完整批次时原子替换本类别平台证据，失败到无法接纳新证据时保留旧证据和原取得时间。用户证据、草稿、其他类别、旧报告版本与迟到任务隔离规则不变。成功完整重查清除旧诊断。

任一计划类别为 partial，则整体 tianyan_status 为 partial，不能触发 empty 快照预填充。分析输入改变则增加 evidence_version，报告按本次实际材料和覆盖生成；无证据仍跳过模型。字典及固定提示词增加“部分结果不能外推全部”的要求。

## 6. 异常 / 错误契约

### WINDOW-ERR-01

不新增或模糊 HTTP 鉴权/额度错误。沿用 UPSTREAM_AUTH、UPSTREAM_LIMIT、UPSTREAM_INVALID、UPSTREAM_INCOMPLETE 等；明确区分主动有限查询和请求失败。只有本轮范围有限时不使用“余额不足”“权限不足”等提示。

未知总数显示未提供，不填 0；同一来源真正重复仍失败，跨来源相同 ID 按已修复命名空间区分。总容量不足不删除既有记录、不自动提高 200 条或 256 KiB 分析输入上限。

## 7. 非功能规格

### WINDOW-NFR-01

本次司法最多执行 6 个第一页业务调用；每个调用沿用现有 8 秒超时与最多一次瞬时错误重试，鉴权/额度不自动重试。不得自动追完剩余 5,564 条，不调用需 SVIP 的批量代理，不把目录或重试按钮当无限制收费循环。

所有权、24 小时会话期限、固定工作流、服务端凭据、输入 200 条/256 KiB、单条 4,000 字符、脱敏诊断与官网只由人浏览等原有约束保持。

## 8. 业务硬规则

### WINDOW-RULE-01

- 有限范围必须在 UI、QueryCoverage 和模型输入一致体现；不是只换一个状态文案。
- 不凭案件数作风险评级，不把各来源/案件阶段重复计为独立事件。
- 不因购买 VIP 就承诺数据完整，不因本次 partial/目录空就判定企业没有风险。
- 不用程序抓取官网或自动解析用户浏览页面补充证据。
- 既有类别完整性规则仅在本稿确认后对司法窗口定向变更，其他类别仍按原契约完整取得。
